# Film X 开发准则

> 本文把当前项目的配置、架构约束和产品边界固化为后续开发规则。优先级从高到低为：用户当前明确需求、实际可执行配置与类型约束、本文。本文不会授权超出用户需求的外部服务、上传或发布操作。

## 1. 必须遵守的工作方式

1. 依赖和脚本必须使用 pnpm，并经 mise 运行：

   ~~~sh
   mise exec -- pnpm <script>
   ~~~

2. 修改前先定位职责边界和数据来源。不要为了方便把页面编排、领域状态、图像算法和基础 UI 混入同一文件。

3. 不改变本地优先边界。除非需求明确改变产品范围，不新增图像上传、远程处理、第三方遥测或服务端持久化。

4. 保持改动最小且内聚。不要在同一修改中顺手重构无关模块、替换无关设计或复制已有基础能力。

5. 未经明确需求，不应假定可用后端、数据库、身份认证、文件持久化、CI 或测试框架。

## 2. 代码放置、状态与类型

| 内容 | 应放位置 | 要求 |
| --- | --- | --- |
| 页面流程、页面 SEO、服务编排 | app/pages | 页面负责连接，不承载底层图像算法。 |
| 领域展示与交互 | app/components/film | 以 props 输入、具名 emits 或 v-model 上报状态变化。 |
| 拼图领域 UI | app/components/film/composition | 工作区上报交互增量，编辑器更新共享状态。 |
| 基础 UI 原语 | app/components/ui | 优先复用已有 Button、Switch、Dialog、Progress、Sonner。 |
| 响应式状态、异步流程、生命周期 | app/composables | 可复用逻辑不能散落在多个页面或展示组件中。 |
| 纯计算与浏览器图像工具 | app/utils | 不持有 Vue 状态，不引入 UI 文案。 |
| 跨模块模型、有限选项、边界常量 | app/types | 使用联合类型和显式接口，不以任意字符串或 any 绕过约束。 |

- 使用 script setup lang="ts"，类型仅导入时使用 type import。
- 共享状态应有清晰的单一来源。子组件不可直接修改不属于自己的外部深层状态。
- 新功能优先从领域类型与 composable 设计，再接入页面和组件。
- 同一业务规则不得在多个组件复制魔法数字；画布、齿孔和格式等边界应复用或扩展已有常量与工具。

## 3. 图像、Canvas 与异步资源规则

1. 输入格式只通过 app/utils/image.ts 的集中定义校验；组件不得另行维护格式白名单。

2. DecodedImage 必须释放。替换图像、移除图像、丢弃过期异步结果和组件卸载时均调用 dispose。

3. 不可绕过串行解码策略。大尺寸图片和 TIFF 的自动识别、预览、导出必须保持串行，或在修改前明确证明新的并发上限不会抬高不可接受的内存峰值。

4. 异步图像任务须抵抗竞态。活动预览使用 token，拼图槽位使用版本号；新增异步链路应采用同等的失效保护。

5. 临时 Canvas、ImageBitmap、Object URL、requestAnimationFrame、定时器和 pointer capture 都需要配对清理。编写逻辑时同时覆盖成功、异常、替换、取消和卸载路径。

6. 不可靠的自动分割不能主动丢弃像素。修改检测算法时保留低置信度时 gap 为 0 的保护语义，除非产品需求明确改变它。

7. 拼图主画布最长边不得绕过 8000 px 上限；齿孔带宽度不得绕过 24 至 240 px 限制。最终输出尺寸必须使用既有的输出 geometry 计算。

## 4. 国际化、错误反馈和可访问性

1. 新增用户可见文案、错误、Toast、SEO 文本、title 与 aria-label 时，同步更新 i18n/locales/en.json 和 i18n/locales/zh-CN.json，且保持键路径一致。

2. 页面 SEO 使用响应式语言 getter，例如 title: () => t('meta.pageTitle')，避免语言切换后元信息过期。

3. 新增可预期错误时，扩展 AppErrorCode、errors.* 翻译键和对应的中文/英文文本；展示时经 useTranslatedError 和 Toast 转译，不向用户暴露底层异常内容。

4. 图标按钮必须有可翻译的 aria-label；纯交互按钮使用 button 语义和明确 type。

5. 拖放功能必须保留文件选择入口。清空队列、删除等破坏性动作应保留或新增清晰的确认机制。

6. 修改响应式布局时同时验证窄屏堆叠和 lg 桌面多栏布局；不可只按桌面视图做判断。

## 5. UI 与样式规则

1. Tailwind 工具类优先；普通界面使用语义颜色 token，例如 bg-background、text-foreground、border-border、bg-card、text-muted-foreground。

2. 不要为普通界面硬编码浅色或深色。图片编辑工作台、透明棋盘格、胶片纹理等确有视觉语义的局部区域可使用受限的局部颜色。

3. 重复且跨组件的视觉规则才进入 app/assets/css/main.css；组件专属的复杂样式使用 scoped style，避免扩大全局影响范围。

4. 保持现有 neutral 主题、CSS Variables、reka-vega 和 Lucide 约定。新增基础组件前先判断能否复用 app/components/ui 中的原语。

5. 保持现有产品视觉语言：细边框、圆角面板、清晰状态反馈、深色图像工作台，以及移动端优先的布局方式。

## 6. 格式、静态检查与验证

必须遵守 .oxfmtrc.json：

- 单行最大 100 字符。
- 不使用分号。
- 使用单引号。
- 不使用尾随逗号。

Oxlint 将 correctness 视为错误，suspicious 与 perf 视为警告。禁用规则必须极少、局部，并紧贴说明原因。现有 no-await-in-loop 仅用于串行解码和导出的内存安全场景，不可当作一般性先例。

完成代码修改后，至少运行：

~~~sh
mise exec -- pnpm check
git diff --check
~~~

若修改涉及 Nuxt 配置、依赖、构建产物、Canvas/浏览器类型边界或重要功能路径，额外运行：

~~~sh
mise exec -- pnpm build
~~~

如果某项验证无法运行，应记录具体命令、失败原因和未覆盖的风险，不能把未执行描述为已通过。

当前项目没有测试基建。若要引入 Vitest、Playwright 或其他测试工具，应先明确依赖变更、要覆盖的关键图像边界、执行环境和 CI 策略，不能把它作为无范围的附带改动。

## 7. 文档与版本控制卫生

- 功能说明应从当前代码、配置和实际 UI 推导；README 不是功能存在的唯一证据。
- 文档与代码同步更新，尤其是输入格式、导出格式、画布边界、路由、脚本和语言范围。
- 不提交 .nuxt、.output、node_modules、.pnpm-store、sample、.env 或 .env.* 中的内容；遵循 .gitignore。
- 提交前检查改动范围，不混入无关文件；只有用户明确要求时才创建提交、推送或拉取请求。
